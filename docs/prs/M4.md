# M4: Contract v0, mock server, TS client 📱

Branch `m4-contract-v0`, stacked on `m3-projects-layers` (PR #4). Goal: Selorm can build the mobile
app against realistic responses before the real sync exists.

## What is in this PR

- **Contract export** with stable operation ids and tags, RFC 9457 `Problem` responses on every
  operation, `X-Org-Id` documented on tenant operations, and examples on every schema and on the
  sync/attachment operations (`common/openapi.py`).
- **Sync and attachment stubs** returning 501 problem JSON, with Pydantic schemas that mirror
  `packages/schema/schemas/sync.schema.json` and the engineering notes' attachment flow. A test
  validates the examples against the JSON Schema in both directions.
- **Contract drift check:** `contract/openapi.json`, `contract/examples/*.json` and the generated
  `packages/api-client/src/schema.ts` must equal the live export; `make contract` regenerates all three.
- **Prism mock:** `make mock` (static examples, :4010), `make mock-dynamic`, `make mock-test`
  (every phone endpoint; also in CI).
- **`@precisecapture/api-client` 0.1.0:** generated types plus a typed fetch client (bearer,
  `X-Org-Id`, `Idempotency-Key`, `ApiError`, single-flight refresh, login/OTP/logout helpers).
- `contract/CHANGELOG.md` v0.1.0 and git tag `contract-v0.1.0`.

## Summary for Selorm

- **Contract:** `contract/openapi.json` (tag `contract-v0.1.0`), docs UI at `/api/v1/docs` on a dev server.
- **Mock:** `make mock` → `http://localhost:4010`. Static examples; any bearer token is accepted;
  send `X-Org-Id` anyway so the real server works unchanged. Error paths are documented but not simulated.
- **Client:** `@precisecapture/api-client` (workspace package). Inject `fetch` and a `TokenStore`
  backed by the OS keystore. `api.login(...)` / `api.verifyOtp(...)` store tokens; any 401 triggers one
  refresh and a retry; `onSignedOut` fires when the refresh fails. `ApiError.fieldErrors` maps
  problem `errors[]` by field.
- **Shapes to build against now:** `PushRequest` / `Change` / `ChangeMeta`, `PushResponse` /
  `ChangeResult`, `PullResponse` / `PullItem` (identical to `sync.schema.json`), `AttachmentCreateIn`
  → `AttachmentUploadOut` (multipart upload id + presigned part URLs, 8 MB parts) → `complete`.
- **Until M6/M7** push, pull and attachments return 501 on the real server; everything else is live.
- **Breaking changes:** none (first version).
