# M7: Attachments (resumable uploads) 📱

Branch `m7-attachments`, stacked on `m6-sync` (PR #7).

## What is in this PR

- **`Attachment`** tenant table (client UUIDv7 id, feature, field key, content type, size, SHA-256,
  storage key `org/{org}/project/{project}/feature/{feature}/{id}.{ext}`, upload status, multipart
  upload id, EXIF fields, thumbnail key, metadata, who/which device). Under the generic isolation test.
- **Flow** (ENGINEERING_NOTES.md §5): `POST /attachments` starts an S3 multipart upload and returns
  presigned 8 MB part URLs (1 h); `GET /attachments/{id}/upload` resumes with only the missing parts;
  `POST /attachments/{id}/complete` completes, checks the stored size, streams the object once to verify
  the SHA-256, then queues post-processing (thumbnail 320 px, EXIF GPS and time).
- **Reads:** `GET /attachments/{id}` (15-minute presigned download and thumbnail URLs),
  `GET /features/{id}/attachments`, `GET /projects/{id}/reports/missing-attachments` (managers).
- Attachments of deleted features are retained.
- **Storage in CI:** a `versity/versitygw` container (MinIO images are no longer pullable); locally MinIO
  as before. Contract v0.2.0 (additive).

## Summary for Selorm (📱 checkpoint)

1. `POST /attachments` with `{id (UUIDv7), feature_id, field_key, content_type, size, checksum_sha256,
   captured_at}` → `{upload_id, part_size, parts: [{part_number, url}], expires_at}`.
2. `PUT` each part body (bytes `(n-1)*part_size .. n*part_size`) to its URL; keep the returned `ETag`.
3. `POST /attachments/{id}/complete` with `{upload_id, parts: [{part_number, etag}]}` (parts may be
   empty: the server lists what it has). 422 `missing_parts` → call `GET /attachments/{id}/upload` and
   send the listed parts. 422 `mismatch` (checksum/size) → the upload is `failed`; fix the file or the
   hash and `GET .../upload` to restart.
4. Re-posting `POST /attachments` with the same `id` is safe: it resumes.
5. Sync the feature first, photos after (`GET /attachments/{id}` gives `download_url` for display).
